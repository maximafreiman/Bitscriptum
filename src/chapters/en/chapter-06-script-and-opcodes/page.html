Chapter 6 · 6.1
A small program behind every transaction
What is Bitcoin Script?

Every Bitcoin transaction that has ever existed includes one question and one answer. The question is in the output: "Who can spend this bitcoin?" The answer is in the next transaction’s input: "Here is the proof that I’m entitled to spend it." Both of these are encoded in a small program called Script.

How Script works

Script is a stack-based language. No variables, no loops, no functions. There are only two things: data and commands. Data is pushed onto the stack (push). A command takes data from the stack, does something, and returns the result (pop). Execution runs left to right, one instruction at a time.

Imagine a stack of plates. You can place a plate on top (push) or take a plate from the top (pop). Script works exactly like this, but the contents are data and computation results.

Why not Turing complete?

Satoshi deliberately designed Script not to be Turing complete. No loops, no recursion, no conditions that can run without bound. This isn’t a shortcoming, but a very deliberate design decision. Every node in the network has to verify every transaction. If Script could contain unbounded loops, one malicious transaction could paralyze the entire network. With limited Script, execution time is always predictable and short.

scriptPubKey and scriptSig

scriptPubKey is the "padlock" placed on the output. It defines the conditions that must be met to spend that output. scriptSig is the "key" carried by the sender of the next transaction. It contains the data needed to satisfy the conditions in scriptPubKey. For SegWit transactions, scriptSig is replaced or complemented by the witness field, which works on the same principle but more efficiently.

Script is one of the most frequently misunderstood parts of Bitcoin. Many think Bitcoin can only do simple transactions. But with Script, Bitcoin can express very complex spending conditions, from multisig to time-locked transactions, all without a central server and without trust.

Chapter 6 · 6.2
The commands that run Script
Opcodes

Script consists of two kinds of elements: data and opcodes. Data is the value pushed onto the stack. Opcodes are the commands that operate on that data.

Categories of opcodes

Stack operations manipulate the stack contents without computation. OP_DUP duplicates the top value. OP_DROP discards it. OP_SWAP swaps the top two values. Arithmetic operations do simple math: OP_ADD adds, OP_SUB subtracts. Comparison operations compare values: OP_EQUAL pushes TRUE if equal, OP_EQUALVERIFY immediately fails the script if not equal. Crypto operations do cryptography: OP_SHA256 hashes, OP_HASH160 is used to make addresses, OP_CHECKSIG verifies signatures. Flow control directs execution: OP_IF for conditions, OP_VERIFY to ensure a value is TRUE, OP_RETURN to create an unspendable output.

Disabled opcodes

Bitcoin once had more expressive opcodes, including string operations, multiplication, and bitwise operations. Most were disabled in 2010 after security flaws were found. Operations like OP_CAT could make the stack grow exponentially and be used for DoS attacks. OP_MUL and OP_DIV could potentially crash nodes due to poorly defined edge-case behavior. This is an example of how Bitcoin chooses security over features.

OP_RETURN

OP_RETURN deserves a mention of its own. It stops script execution entirely and marks the output as provably unspendable, impossible to spend, not because of a wrong key, but because the script is designed never to produce TRUE. It’s used to embed small data into the blockchain: a document hash, a message, or other metadata. The data size limit is not a consensus rule but relay policy that can differ per node and implementation — long-standing convention: 80 bytes.

Miniscript

Writing Bitcoin Script manually is very error-prone. A script that looks correct can have subtle bugs that cause funds to be locked forever or stolen. Miniscript is a structured language that compiles to Bitcoin Script, designed so that scripts can be analyzed automatically: can they be spent, what’s the cost, are there conflicting conditions?

Miniscript defines a set of "fragments" that can be combined safely: single keys, multisig, timelocks, hash preimages, and their combinations with AND, OR, and threshold. Each fragment has a strict type so the compiler can verify that the resulting script can really be executed as intended. A wallet that supports Miniscript can read any script made with Miniscript and immediately know its spending conditions.

With about 200 defined opcodes, most of them inactive, Bitcoin Script looks simple. But it’s this simplicity that makes it safe. Every active opcode has been tested and audited for over a decade. No surprises.

Chapter 6 · 6.3
Bitcoin’s most classic transaction format
P2PKH

P2PKH stands for Pay-to-Public-Key-Hash. This is the most classic and most widely used Bitcoin transaction format since Bitcoin was born. If you’ve ever seen a Bitcoin address starting with the number 1, that’s P2PKH.

How P2PKH works

The idea is simple: instead of stating the recipient’s public key directly in the output, what’s stored is the hash of that public key. This is the "Public Key Hash" in P2PKH. When someone wants to spend a P2PKH output, they have to prove two things: first, that they know the public key that produces that hash. Second, that they have the private key matching that public key, proven with a digital signature.

scriptPubKey P2PKH

scriptPubKey is the "padlock" placed on the output. For P2PKH, its form is always the same: OP_DUP OP_HASH160 <Public Key Hash> OP_EQUALVERIFY OP_CHECKSIG. It means: anyone who can prove they know the public key whose hash is this, and can sign with the matching private key, may spend this output.

scriptSig P2PKH

scriptSig is the "key" carried by the sender. For P2PKH there are only two elements: <Signature> <Public Key>. Very simple.

The verification process

The node combines scriptSig and scriptPubKey, then runs them as a single script. The stack runs from left to right. OP_DUP duplicates the public key. OP_HASH160 hashes one copy of it. OP_EQUALVERIFY compares the hash result with the hash stored in the output. If they match, OP_CHECKSIG verifies the signature against the public key. If everything succeeds, the result is TRUE and the transaction is valid.

Why a hash, not the public key directly?

Because the hash provides an extra layer of security. As long as the output hasn’t been spent, the public key is never exposed on the blockchain. Only its hash appears. This means even if one day quantum computing can break elliptic curve cryptography, bitcoin that has never been spent is still protected by the hash.

P2PKH has existed since Bitcoin’s first block. Even though there are now more efficient formats like P2WPKH, P2PKH remains valid and is still widely used. Backward compatibility is one of Bitcoin’s core principles.

Chapter 6 · 6.4
Separating the signature from the transaction
P2WPKH and SegWit

P2PKH worked well for years. But as Bitcoin grew, there was an increasingly pressing problem: full blocks, expensive fees, and one technical flaw called transaction malleability.

Transaction malleability

Transaction malleability is the ability of a third party to change a transaction’s Transaction ID (txid) without invalidating the transaction. This is possible because the txid is computed from the entire transaction data including scriptSig, and scriptSig can be modified slightly without making the signature invalid. Malleability made the Lightning Network and more complex payment channels very hard to build on top of Bitcoin.

SegWit (Segregated Witness)

SegWit was activated in August 2017 through a soft fork. The idea is elegant: separate the signature data (witness data) from the main transaction data. In a SegWit transaction, scriptSig is emptied. The signature data is moved to a separate structure called the witness field. Because the txid is now computed only from the transaction data without the witness data, transaction malleability is fully resolved. As a bonus, witness data gets a fee discount: one byte of witness is counted as 0.25 vbyte, not 1 byte.

P2WPKH

P2WPKH stands for Pay-to-Witness-Public-Key-Hash, the SegWit version of P2PKH. Its scriptPubKey is far shorter: just OP_0 <Public Key Hash>. OP_0 marks this as SegWit version 0, followed by the 20-byte public key hash. The signature and public key are no longer in scriptSig, both are in the witness field which is processed separately.

P2WPKH address

P2WPKH addresses use the bech32 format starting with bc1q. This format uses only lowercase letters, contains no confusing characters like 0, O, I, and l, and has better error detection than Base58Check.

Compatibility

Old nodes that don’t understand SegWit see the scriptPubKey OP_0 <hash> as an output that’s always spendable. This is intentional as part of the soft fork design: old nodes don’t need to validate witness data, they just need to not reject it.

SegWit is one of the biggest upgrades in Bitcoin’s history. It resolved transaction malleability, made fees more efficient, and opened the way for the Lightning Network. All of this was achieved through a soft fork, without splitting the network.

Chapter 6 · 6.5
Hiding complex spending conditions
P2SH and Multisig

Imagine a company that wants to store bitcoin with a rule: no single person can move the funds alone. At least 2 of 3 directors are required to approve each transaction. How does Bitcoin express this rule?

P2MS (bare multisig)

Before P2SH, Bitcoin had a multisig format called P2MS or Pay-to-Multisig. The script places all public keys directly in scriptPubKey: OP_2 <pubkey1> <pubkey2> <pubkey3> OP_3 OP_CHECKMULTISIG. The problem is that all public keys are exposed on the blockchain from the moment the output is created. Worse, there’s no standard address format for P2MS. The sender has to know the full script structure, not just an address.

P2SH (Pay-to-Script-Hash)

P2SH was activated in 2012 as a soft fork. The idea is brilliant: hide the complex script behind a hash. The recipient creates a redeem script that defines the spending conditions, then hashes it. This hash is what’s put into scriptPubKey: OP_HASH160 <redeem script hash> OP_EQUAL. Only 3 elements. The actual script is only revealed when the output is spent.

P2SH address

The hash of the redeem script is encoded using Base58Check with a prefix that produces an address starting with the number 3. The sender only needs to know this address without needing to know the multisig structure inside it.

P2SH advantages

First, privacy: the complex condition script isn’t exposed until the moment it’s spent. Second, standardization: the recipient can give a normal address without having to explain their multisig structure to the sender. Third, the burden on the recipient: the cost of including the long script is borne by the recipient when spending, not the sender when creating the output.

P2SH-P2WPKH

P2SH can also wrap a SegWit script, called P2SH-P2WPKH or wrapped SegWit. It’s used as a middle ground for old wallets that don’t yet support bech32 but want to enjoy SegWit’s benefits. The address still starts with 3 but contains a witness program inside.

P2SH changed how Bitcoin expresses complex spending conditions. Instead of putting all the logic in the output, the logic is hidden behind a hash. This is an example of how Bitcoin evolves through elegant abstraction, without changing the basic rules.

Chapter 6 · 6.6
Prove only what needs to be proven
Taproot and P2TR

Taproot was activated in November 2021 through a soft fork. It’s the biggest Bitcoin upgrade since SegWit, and brings three changes at once: Schnorr signatures, MAST, and a new output format called P2TR.

The problem Taproot solves

Before Taproot, there were two nagging problems. First, privacy: multisig transactions, lightning channels, and simple transactions looked different on the blockchain. Anyone could see that an output was multisig or a smart contract just from the shape of its script. Second, efficiency: a complex script with many conditions had to include all the conditions when spent, even conditions that weren’t used.

Schnorr signature

Schnorr signatures replace ECDSA for Taproot transactions. Their main advantage is key aggregation: several public keys can be combined into a single public key. This means a 3-of-5 multisig can look exactly like an ordinary single-signer transaction on the blockchain. No one can tell them apart just from looking at the output.

MAST (Merkelized Alternative Script Trees)

MAST allows an output to have many alternative spending conditions, each as a branch of a Merkle tree. When spending, the sender only needs to reveal the branch used, not the entire tree. Unused branches stay hidden forever. This saves space on the blockchain and preserves the privacy of unused conditions.

P2TR (Pay-to-Taproot)

P2TR combines Schnorr and MAST in one elegant output format. Its scriptPubKey is very simple: OP_1 <tweaked public key>. OP_1 marks SegWit version 1, followed by a 32-byte public key that has been modified to include a commitment to the entire script tree. A P2TR output can be spent with the key path (a direct Schnorr signature) or the script path (revealing one of the MAST branches).

P2TR address

P2TR addresses use the bech32m format starting with bc1p. Unlike the bech32 used by P2WPKH, bech32m has an updated checksum to handle different witness program lengths.

Tapscript

Tapscript is the version of Script used inside the Taproot script path spending. It is not a new language, but a revision of the old Script with several important changes. OP_CHECKSIG remains and now works with Schnorr signatures. What was disabled is OP_CHECKMULTISIG, replaced by a new opcode called OP_CHECKSIGADD. This enables more efficient multisig because all signatures can be checked in parallel, not one by one like in the old Script.

Tapscript also introduces OP_SUCCESS: a group of opcodes that currently always produce success. This is not a bug, but a deliberate design to make it easier to upgrade Script in the future without a hard fork. If one day a particular OP_SUCCESS is given new meaning through a soft fork, old scripts using it automatically support the new semantics.

Taproot isn’t just a technical upgrade. It’s a philosophical shift: from "prove everything" to "prove only what needs to be proven." Unused conditions don’t need to be revealed. This makes Bitcoin more private, more efficient, and more expressive all at once.
