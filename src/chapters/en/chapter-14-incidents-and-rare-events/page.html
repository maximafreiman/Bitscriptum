Chapter 14 · 14.1
184 billion bitcoin created in one block — and fixed in 5 hours
The 2010 Value Overflow Bug

On August 15, 2010, someone found a critical bug in the Bitcoin code: an integer overflow. By exploiting this bug, the attacker managed to create a transaction that appeared to create bitcoin far beyond the protocol’s rules. This transaction was briefly confirmed in block #74,638 before being rolled back by the community in about 5 hours. It’s important to understand: this was a bug in the code implementation, not a bug in the Bitcoin protocol itself. The 21 million BTC supply was never truly threatened.

Two things to distinguish

Bitcoin has two different limits that are often confused. First, MAX_MONEY: this is a Bitcoin protocol consensus rule that states no transaction output may exceed the total supply of 21 million BTC (2.1 quadrillion satoshi). Second, MAX_INT64: this is the mathematical limit of the 64-bit integer data type in computers, namely 9,223,372,036,854,775,807. This number has nothing to do with Bitcoin’s rules, it’s just the technical limit of storing numbers in computer memory. This bug isn’t about violating MAX_INT64, but about code that forgot to check MAX_MONEY before performing the addition.

How the bug works

The Bitcoin code at the time didn’t check whether the value of each transaction output exceeded MAX_MONEY before adding them up. The attacker took advantage of this by creating two outputs that each far exceeded 21 million BTC. When the two were added together, the total exceeded MAX_INT64 and an integer overflow occurred: the number "wrapped" into a large negative number. The validation code then checked whether the total output was less than the total input, and because the total output had become a negative number, this condition was always met. The transaction passed validation when it shouldn’t have.

The community response

Satoshi Nakamoto himself responded to this incident. In about 5 hours, Satoshi released a patch that added a check: if an output value is less than zero or exceeds MAX_MONEY, the transaction is immediately rejected. The Bitcoin community at the time, which was still very small, managed to organize an emergency soft fork: nodes upgraded and started ignoring block #74,638. The clean chain became dominant. The bitcoin that appeared to be "created" never really existed because it was immediately rolled back before anyone could use it.

This bug is an example of the important difference between a protocol bug and an implementation bug. The Bitcoin protocol defines the rules correctly, but the code that implements those rules had a gap. This is one reason Bitcoin’s consensus code is audited very strictly: a single missing line of code can create a dangerous gap.

Eight years later, it almost happened again

It is tempting to file the 2010 incident under growing pains: the code was raw, the users were few, gaps were to be expected. But in September 2018 Bitcoin came close to losing the 21 million cap a second time, and this time in a mature era, with code under far heavier review.

The bug is catalogued as CVE-2018-17144. It came not from a new feature but from an optimization. In Bitcoin Core 0.14.0, released in March 2017, a duplicate-input check was removed because it was believed to happen elsewhere already, so repeating it only cost time. That belief was wrong. As a result, nodes were willing to partly process blocks that spent the same input more than once.

In the 0.14.x versions the consequence was "only" that the node died abruptly, because a safety check deliberately halted the program on encountering an impossible state. But that check was rewritten in 0.15.0, and from then on the node no longer stopped. It carried on. Which meant a miner could spend one output twice inside a single block and claim its value twice as well. Repeated enough times, that is minting Bitcoin out of thin air.

The bug lay dormant for about a year and a half. What finally surfaced it was not the core team but a developer using the alias awemany, from the Bitcoin Cash camp, while reading code his project had inherited from Bitcoin Core. He disclosed it privately on 17 September 2018, and not only to Bitcoin Core but to other projects running the same code.

What he reported was only a crash bug. It was the Bitcoin Core developers themselves who then realised the same root cause carried something far worse: inflation. At that point they faced an uncomfortable choice. Full disclosure meant telling everyone how to mint Bitcoin before most nodes had a chance to update. Saying nothing meant leaving the hole wide open.

The path they took was staged disclosure: announce and patch the lesser crash bug in the open, so that people had an urgent reason to upgrade immediately, while quietly reaching out to miners and large businesses about the real issue. The fix shipped on 18 September in version 0.16.3, less than a day after the report arrived. The full impact was only announced on 20 September, once most of the network was safe.

The bug was never exploited. But its lessons cut deeper than those of 2010, and there are three. First, the most dangerous change is often not an addition but the removal of something believed unnecessary. Second, the person who found it came from a rival project reading inherited code, which makes open source not merely an ideal but a defence mechanism that demonstrably works. Third, Bitcoin’s security does not end with the mathematics we covered in Chapter 4. It also rests on humans reading code carefully, and on hard judgement calls about when a danger is best made public.

Chapter 14 · 14.2
When Bitcoin’s history is rewritten — and why that’s normal
Chain Reorganization (Reorg)

A reorg, short for chain reorganization, happens when a node finds that there’s an alternative chain longer than the chain they’re currently following. The node then switches to the longer chain, discarding the blocks that are no longer part of the longest chain. These discarded blocks are called orphan blocks.

Small reorgs are normal

A 1-2 block reorg is a routine event that happens almost every day in Bitcoin. This can happen when two miners find a valid block almost simultaneously: the network is temporarily split because some nodes receive miner A’s block first, while others receive miner B’s first. As soon as one of the miners finds the next block, its chain becomes longer and the whole network converges to that chain. The losing miner loses the block reward but the network stays safe.

A large reorg is dangerous

A deep reorg, 6 blocks or more, requires very large hash rate and can be exploited for a double spend. An attacker with enough hash rate can mine an alternative chain in secret, do a large transaction on the main chain (for example selling bitcoin to an exchange), then release the longer alternative chain that doesn’t contain that transaction. A merchant or exchange that already considered the transaction final could become a victim.

The history of reorgs in Bitcoin

The deepest reorgs ever recorded on Bitcoin mainnet were not attacks at all, but fallout from software bugs. Rolling back the 2010 overflow bug we covered in 14.1 required reversing dozens of blocks, and the March 2013 chain split we will cover in 14.3 ran for 24 blocks. Outside those two incidents, reorgs on Bitcoin are almost always just 1 to 2 blocks. Deliberate deep reorgs have happened on other networks like Ethereum Classic (a 100+ block reorg in 2019) and Bitcoin Gold, but both have far smaller hash rate than Bitcoin so the cost of attack is far lower.

The "6 confirmations" standard often mentioned in Bitcoin isn’t an arbitrary number. It’s an estimate that after 6 blocks, the cost of doing a reorg deep enough to cancel that transaction becomes very uneconomical for any attacker. For small everyday transactions, 1-3 confirmations is already safe enough.

Chapter 14 · 14.3
When two software versions produced two different realities for 6 hours
March 2013 Chain Split

On March 11, 2013, an unintended chain split occurred between nodes running Bitcoin 0.7 and Bitcoin 0.8. This wasn’t an attack, wasn’t a deliberate bug exploit, but an unexpected consequence of a difference in database implementation between two software versions that both claimed to follow the same rules.

The root cause: BerkeleyDB vs LevelDB

Bitcoin 0.8 switched the storage database from BerkeleyDB to LevelDB as a performance optimization. What wasn’t realized: BerkeleyDB had a limit of 10,000 keys that could be locked simultaneously. This wasn’t part of Bitcoin’s consensus rules, just an implementation detail. LevelDB didn’t have the same limit. Block #225,430, mined on the night of March 11, affected the status of more than 5,000 transactions at once, requiring more than 10,000 BerkeleyDB keys simultaneously. Bitcoin 0.7 nodes couldn’t process this block and rejected it. Bitcoin 0.8 nodes accepted it without issue.

Six hours with two Bitcoins

For about 6 hours, there were two versions of Bitcoin running in parallel. The 0.8 chain had about 60% hash rate so it grew faster. The split lasted for 24 blocks before being resolved. The split wasn’t detected immediately: it was only about an hour later, at 23:10 GMT, that a user named thermoman reported an anomaly on the bitcoin-dev IRC. One minute later, Mark Karpelès of Mt. Gox immediately halted block processing as a precaution.

An unusual solution

The community had to choose: upgrade everyone to 0.8, or go back to 0.7? The decision was to go back to 0.7, not because 0.7 was more technically correct, but because it was easier to coordinate a handful of large mining pools to downgrade than to force the entire ecosystem to upgrade at once. BTCGuild and Slush Pool downgraded even though they had to give up the reward they’d already earned on the 0.8 chain. At block #225,454, the 0.7 chain managed to surpass the 0.8 chain and the network reunited.

The recorded double spend

During the split period, one double spend was recorded. But according to BIP 50, the official post-mortem written by Gavin Andresen, this was done by someone experimenting to test whether it was possible, not with intent to steal.

This incident taught an important lesson: two implementations that claim to follow the same rules can still produce different behavior because of hidden implementation details. This is one reason Bitcoin is very careful about changing consensus code, and why there’s a big effort to ensure all implementations behave identically on every edge case.

Chapter 14 · 14.4
A mining strategy that’s profitable on paper — but has never been proven to work
Selfish Mining

Selfish mining is a strategy where a miner with significant hash rate hides the blocks they manage to find and doesn’t immediately broadcast them to the network. By withholding these blocks, they gain an advantage: they can start mining on top of the hidden block while the network is still mining on the previous block.

How selfish mining works

If the dishonest miner manages to find the next block before the network knows about their hidden block, they can release two blocks at once and turn the other honest block into an orphan. The honest miner who worked hard to find a block loses their reward, while the dishonest miner gets the reward of two blocks at once.

Formal analysis and the threshold

This attack was first formally analyzed by Ittay Eyal and Emin Gun Sirer in their 2013 paper. They showed that with about 33% hash rate, selfish mining can be economically profitable. With larger hash rate, the theoretical profit grows.

The real technical risks

Although it looks profitable on paper, selfish mining has serious technical risks. First, block secrecy is hard to maintain on a P2P network: once a block is found, the propagation signal on the network can leak before the dishonest miner is ready to release their hidden chain. Second, if an honest miner finds a block before the dishonest miner releases their chain, all the hidden work becomes wasted and the dishonest miner loses all the reward they’d invested. Third, the longer they hide blocks, the greater the risk that the hidden chain can never catch up to the public chain. Fourth, an abnormal orphan pattern can be detected by the community and cause a boycott of the suspicious pool.

Why it has never happened in Bitcoin

In practice, selfish mining has never been proven to happen at a significant scale. There are several reasons: it’s hard to maintain secrecy on a peer-to-peer network, the risk of losing rewards is far more real than the theoretical profit, the distributed mining pool landscape makes it very hard for one entity to reach 33% hash rate without being noticed, and the economic incentive for honest mining remains stronger in the long term.

Selfish mining is a reminder that Bitcoin’s economic incentives are designed to make dishonesty more expensive than honesty. But this isn’t an absolute guarantee: if the mining landscape changes drastically and one entity dominates the hash rate, these incentive dynamics could change.

Chapter 14 · 14.5
An attack that isolates one node, not the whole network
Eclipse Attack

An eclipse attack is an attack where the attacker controls all of a target node’s peer connections, so that node only communicates with nodes controlled by the attacker. It’s important to understand from the start: this is an attack against one specific node, not against the Bitcoin network as a whole. The Bitcoin network keeps running normally.

A simple analogy

Imagine you live in a big city but all your information sources, neighbors, friends, radio, and TV, are replaced by an attacker’s agents delivering fake news. You’re still in the same city, but you don’t know what’s really happening. The city itself keeps running normally without you. That’s an eclipse attack: the attacked node lives in a fake reality controlled by the attacker, while thousands of other nodes on the network keep operating correctly.

How an eclipse attack works

Every Bitcoin node maintains a number of connections to other peers. If the attacker can fill all these connection slots with nodes they control, the target node can no longer communicate with the real network. The attacker does this by flooding the network with IP addresses they control, waiting for the target node to restart and pick new peers, or exploiting weaknesses in the peer selection mechanism.

Possible impacts

An eclipsed node can be tricked into accepting fake transactions (a double spend against a merchant), wasting hash rate on a fake chain (for a miner), or exposing transaction information to the attacker before it’s broadcast to the real network. But once again, all these impacts only happen to the node that was successfully isolated, not to the network as a whole.

Mitigations in Bitcoin Core

Bitcoin Core has already implemented several mitigations. Anchor connections maintain 2 outbound connections to trusted nodes even during a restart. Limits on connections from the same IP subnet make it harder for an attacker to dominate all the slots. Tor support and multiple network interfaces make it harder to identify and isolate the target node.

An eclipse attack isn’t proof that Bitcoin is easy to attack or that its decentralization is weak. It’s an attack that requires great effort to target one specific node, and Bitcoin Core keeps improving peer connection resilience to make this attack harder. The network as a whole is actually very hard to attack precisely because it’s distributed across thousands of nodes that don’t depend on each other.

Chapter 14 · 14.6
Not a perfect system — but a system that has been battle-tested for 15+ years
What Keeps Bitcoin Strong?

After studying the overflow bug, chain split, reorg, selfish mining, and eclipse attack, a reasonable question arises: if all these threats exist, why is Bitcoin still standing today?

Aligned economic incentives

Successfully attacking Bitcoin requires a cost far exceeding the gain that can be obtained. Selfish mining is more expensive than honest mining in the long term. An eclipse attack needs large resources for a very specific target. A 51% attack needs astronomical electricity and hardware costs. Honest miners get a larger and more consistent reward than dishonest ones because the system is designed that way.

Extreme network redundancy

There’s no single point of failure in Bitcoin. If one node is attacked, thousands of others keep running. If one implementation has a bug, another implementation can be a reference. If one mining pool is compromised, the remaining hash rate still secures the network. There’s no central server, no CEO to pressure, no off switch.

A vigilant and responsive community

The 2010 bug was found, reported, and fixed in 5 hours. The 2013 chain split was detected in an hour and resolved with extraordinary coordination between developers, mining pools, and exchanges. Developers, miners, node operators, and users all have an incentive to keep the network healthy because Bitcoin’s value depends on trust in the network.

Open source and total transparency

The Bitcoin code can be examined by anyone, anytime. No gap can be hidden for long because thousands of eyes keep watching. Every change is strictly audited before being implemented. Weaknesses that are found are fixed openly and the result becomes a lesson for the entire ecosystem.

Bitcoin isn’t a perfect system. It’s a system that has been battle-tested since 2009, attacked from various directions, and still standing. Every weakness found becomes a lesson. Every failed attack proves the resilience of its architecture. And every incident successfully resolved proves that a distributed community can coordinate without a central authority.
