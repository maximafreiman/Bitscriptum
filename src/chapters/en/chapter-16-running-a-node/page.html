Before it can be trusted, a node must read all of Bitcoin’s history from the start
Initial Block Download — How a New Node Gets to Know Bitcoin

Imagine you just moved to a new city and have to read all the newspapers from the last 15 years before you can follow today’s news. That’s what a new Bitcoin node does: it must validate every block since the genesis block before it can be considered synced and trusted.

This process is called Initial Block Download (IBD). For a new node today, this means validating hundreds of thousands of blocks containing hundreds of millions of transactions. Depending on hardware, this process can take from a few hours to several days.

Headers-first: a clever strategy

Bitcoin client software (like Bitcoin Core or Bitcoin Knots) doesn’t immediately download all blocks from the start. It first downloads all the block headers, 80 bytes per block, from peers. For the entire blockchain, this is only about 70MB. From the headers, a node can verify the chain of proof-of-work without needing any transaction data at all.

After knowing which is the longest valid chain, only then does the node download blocks in parallel from many peers at once. This is far more efficient than the old approach of downloading just one block from one peer sequentially.

What is verified during IBD?

For each block, the node verifies: the proof-of-work is valid, the timestamp is within the allowed range, the block size doesn’t exceed the limit, all transactions are cryptographically valid, there’s no double spend, and the total coinbase output doesn’t exceed the allowed reward. This isn’t a light process, which is why IBD requires significant time and CPU.

assumevalid: a safe shortcut

Many Bitcoin client implementations include the hash of a particular block that has been verified by the broad community as a "safe point assumed valid." For blocks before this point, the node still downloads and executes all transactions to build the UTXO set, but no longer verifies the cryptographic signatures, which is the most CPU-intensive part. This shortens IBD significantly without sacrificing the security of the UTXO set.

Important: assumevalid isn’t blind trust. The node still verifies the entire block structure and the UTXO set. What’s skipped is only the signature verification for old blocks that have already been proven valid by millions of other nodes.

While IBD is in progress, the node should not be used to verify payments. It doesn’t yet have a full picture of the blockchain and can be tricked into accepting a transaction that has already been double-spent in a block it hasn’t validated. Check the "initialblockdownload" field via RPC to make sure the node is ready.

Chapter 16 · 16.2
A node trusts no one — it verifies everything itself
Block Verification — What a Node Checks Every Time a New Block Arrives

Every time a new block arrives from the network, a node doesn’t just accept it. It runs a long, strict series of checks before deciding whether the block is valid or not. This process is what makes Bitcoin trustless: you don’t need to trust anyone because your own node verifies everything.

Two layers of verification

Block verification happens in two layers. The first is header verification: the node checks the proof-of-work, timestamp, and basic block structure without needing to look at the transactions inside. This is fast and light. The second is full verification: the node checks every transaction one by one, ensuring there’s no double spend, all signatures are valid, and all consensus rules are met.

What gets checked?

Proof-of-work: the hash of the block header must be below the current difficulty target. This can’t be faked without expending real energy. Timestamp: no more than 2 hours in the future from the node’s time, and must be greater than the Median Time Past (MTP). Block size: total weight doesn’t exceed 4 million weight units. Coinbase transaction: the reward claimed by the miner doesn’t exceed the block subsidy plus total transaction fees. Every transaction: all inputs refer to a UTXO that exists and hasn’t been spent, all signatures are cryptographically valid, no transaction spends more than it receives.

Script validation: the most complex layer

For every transaction input, the node must run the Bitcoin script and verify that the locking script conditions are met by the provided unlocking script. This involves executing a stack-based virtual machine for every input in every transaction in every block. This is the most CPU-intensive part of the entire verification process.

Parallel verification

Modern Bitcoin client software verifies signatures in parallel using all available CPU cores. This is one reason better hardware speeds up IBD significantly. The more cores, the faster the signature validation process, which can number in the tens of thousands per block.

Every node that runs this verification is one independent vote that enforces Bitcoin’s consensus rules. No single entity can force these nodes to accept a block that violates the rules, even if that block has a valid proof-of-work.

Chapter 16 · 16.3
If you could keep only one folder from all of Bitcoin — keep the chainstate
The Chainstate Database — The Heart of Bitcoin State

If you delete all the blocks from your node’s hard drive but keep one small folder called chainstate, your node can still verify whether a new transaction is valid or not. That folder holds the entire "current state" of Bitcoin, all the UTXOs that exist right now, who owns them, and how much they’re worth.

What is chainstate?

Chainstate is the database that holds the UTXO set: the collection of all transaction outputs that have never been spent. Every time a new block is validated, the node updates the chainstate, new outputs are added, spent outputs are removed. This is a snapshot of current Bitcoin ownership.

LevelDB: A Very Organized Filing Cabinet

On disk, the chainstate is stored using LevelDB, a key-value database created by Google that’s very efficient for fast access. Imagine you have 184 million sheets of documents, where each sheet is one UTXO. If those documents were piled up haphazardly, finding one document could take a long time. LevelDB organizes those documents in order by their key, so a lookup can be done in milliseconds even with hundreds of millions of entries. That’s why a node can verify a new transaction very quickly without traversing the entire blockchain.

The key is the outpoint (txid + output index), the value is information about that UTXO: the value in satoshi, the locking script, whether it’s coinbase, and in which block it was confirmed.

Why does the UTXO set size matter?

Currently the UTXO set contains about 184 million entries and is about 11 GB on disk after LevelDB compression. The larger the UTXO set, the more RAM a node needs for efficient operation. This is one reason the Bitcoin community pays close attention to "UTXO bloat", the practice of creating many small, inefficient outputs.

dbcache: The Size of the Desk in RAM

One of the most important configuration parameters in bitcoin.conf is dbcache, the cache size for the chainstate database in MB. Imagine LevelDB as a physical filing cabinet in a warehouse (the hard disk). Every time the node needs to check a UTXO, it has to walk to the warehouse, open the drawer, grab the document, read it, then put it back. dbcache is the desk in front of the warehouse, the bigger the desk, the more documents can be accessed directly without going back and forth to disk. The default is only 450 MB, but with enough RAM, raising it to 4-8 GB can speed up IBD dramatically.

Undo data: how a node can roll back

Besides chainstate, the node also stores undo data for each block, the data needed to reverse that block’s effects in case of a reorg. Undo data contains all the UTXOs spent in that block, so if that block has to be disconnected, the node can return those UTXOs to the chainstate.

The total of all UTXOs in the chainstate must exactly match the total circulating Bitcoin supply. This can be verified by anyone at any time by running gettxoutsetinfo. There’s no central bank, no external audit needed, mathematics proves it.

Chapter 16 · 16.4
A node that saves storage but doesn’t compromise on verification security
Pruning — Discard Old Blocks, Stay Fully Validating

There’s a common misconception about running a Bitcoin node: that you need hundreds of gigabytes of storage to do it. This isn’t entirely true. Bitcoin has a feature called pruning that lets a node discard old blocks from disk after validating them, while still being able to fully verify new transactions.

What is a pruned node?

A node running in pruning mode still downloads and validates every block since the genesis block during IBD, there’s no shortcut. But after a block is validated and the UTXO set is updated, that block can be deleted from disk. What remains is only the chainstate (UTXO set) and a few recent blocks as a buffer. The result: a node that needs a minimum of about 550 MB of storage instead of 700+ GB for a full archival node.

What you lose with pruning

A pruned node can’t serve old blocks to other peers doing IBD. This means a pruned node doesn’t contribute fully as a relay for the network. Besides that, there are several RPC commands that can’t be run on a pruned node because the data they need is no longer on disk. This is what most often confuses new users.

But the most important thing remains

A pruned node is a fully validating node, not a light client and not an SPV node. The ability to verify new transactions, validate new blocks, reject invalid transactions and blocks, and maintain an accurate UTXO set all remain. Verification security isn’t reduced at all.

Configuring pruning

In bitcoin.conf, pruning is configured with the prune parameter in MB, with a minimum of 550 MB. A value of 0 means pruning is off. There are two modes: automatic, where the node manages itself based on a target size, and manual, where pruning is done via RPC to a particular block height.

A pruned node is very suitable for users who want to verify their own transactions without depending on a third party, but have limited storage. If storage is sufficient, running a full archival node is better for the health of the network because it can help new nodes doing IBD.

Chapter 16 · 16.5
Faster sync doesn’t mean less secure — if designed correctly
assumevalid and assumeUTXO — Faster Sync Without Sacrificing Trustlessness

We touched on assumevalid in 16.1 as one reason IBD can be shortened. This section explains how it actually works, along with its sibling assumeUTXO, and answers the objection that comes up most often: does this mean we are back to trusting the developers?

IBD can take hours or even days. Two Bitcoin features, assumevalid and assumeUTXO, are designed to speed up this process significantly. But both are often misunderstood: they’re not blind trust in the developers, but very carefully designed choices with verification mechanisms that remain strong.

assumevalid: Skip Signature Verification for Old Blocks

During IBD, the most CPU-consuming part is the cryptographic signature verification for every transaction input. For a blockchain hundreds of thousands of blocks long with hundreds of millions of transactions, this is very heavy work and can take dozens of hours.

assumevalid is the hash of a particular block hardcoded into the Bitcoin client software. For all blocks before this hash, the node still downloads all the data, validates the block structure, and builds the UTXO set fully, but doesn’t verify the cryptographic signatures. The logic: if millions of other nodes have already validated these signatures and the blockchain keeps running normally, the signatures must be valid.

Important: you can override this anytime. By running the flag -assumevalid=0, the node will verify every signature from block 0 without exception. This takes far longer but provides the most thorough verification.

assumeUTXO: Start from a UTXO Set Snapshot

assumeUTXO is a newer and more radical feature. Instead of building the UTXO set from the genesis block, the node can load a ready-made UTXO set snapshot from an external file. The node can immediately be used to verify new transactions while verifying the historical blockchain in the background.

The analogy: imagine you just joined a company. Rather than reading all the emails from 15 years ago before you can start working, you read a summary of the current situation first (the UTXO snapshot), start working right away, while slowly reading the historical archive in your free time.

Is this safe?

For assumevalid: if a malicious developer inserted the wrong block hash, the node would build a UTXO set that conflicts with the network and would be caught immediately. The thousands of developers and users who audit the source code become a strong layer of social verification.

For assumeUTXO: the snapshot hash is hardcoded and can be audited by anyone. If the snapshot contains the wrong UTXO, the background historical verification will eventually find the inconsistency. The design ensures that even if the snapshot is wrong, the node will self-correct.

assumevalid and assumeUTXO aren’t shortcuts that sacrifice security, but rather both are very carefully designed optimizations. Bitcoin’s security doesn’t depend on one node verifying everything, but on thousands of independent nodes all running the same consensus rules.

Chapter 16 · 16.6
Without your own node, you have to trust someone — and that contradicts the entire idea of Bitcoin
Why Run Your Own Node — and 10 Daily Commands

After understanding IBD, chainstate, block verification, pruning, and assumevalid, it’s time to answer the most fundamental question: why should you bother running your own node?

"Don’t trust, verify": Not an Empty Slogan

If you don’t run your own node, you have to trust someone. Maybe the exchange where you bought bitcoin. Maybe the block explorer you use to view transactions. Maybe the wallet connected to someone else’s node. Every time you trust a third party to verify a Bitcoin transaction, you create a point of failure that can be manipulated, hacked, or can lie.

Your own node removes all that dependence. You verify for yourself that the transaction you received really is on the blockchain, that there’s no hidden inflation, that the consensus rules you agreed to are actually enforced.

What does your node verify every day?

Every new block: the proof-of-work is valid, no transaction spends a UTXO that doesn’t exist, no miner claims more reward than they should, all consensus rules are met. Every transaction you receive: it really is on the blockchain, confirmed as many times as you see, with no data manipulation from a third party.

A node is your voice in the network

If one day there’s a proposal to change Bitcoin’s consensus rules, for example raising the supply limit or changing the mining algorithm, your node is what determines whether you follow that change or not. A node that isn’t upgraded will automatically reject blocks that violate the old rules. This is the mechanism that makes consensus changes in Bitcoin very hard to do without broad agreement from the users.

Contributing to the network

Every node that runs strengthens the Bitcoin network. An archival node helps new nodes doing IBD. A node that accepts inbound connections helps new peers find the network. The more independent nodes that run, the harder it is for anyone to censor transactions or manipulate data.

Running your own node is the most fundamental form of participation in Bitcoin. Not because it gives a direct financial benefit, but because it’s how you truly own and verify the bitcoin you hold, without trusting anyone.
