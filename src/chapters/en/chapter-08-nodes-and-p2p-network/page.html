Chapter 8 · 8.1
Thousands of computers enforcing the rules without a leader
What is a Bitcoin Node?

When people talk about "Bitcoin", they often only think about the price or the wallet. But behind all of that are thousands of computers around the world that keep running, verifying every transaction and storing a complete copy of the blockchain. These computers are called nodes.

A node is the keeper of the rules

A Bitcoin node isn’t just a database. It’s the keeper of the consensus rules. Every node independently verifies every transaction and every block using the same rules. No one can force it to accept an invalid block, even if that block comes from the largest miner. This is the heart of Bitcoin’s decentralization: there’s no central authority that decides what’s valid. Every node decides for itself, based on the same rules.

Types of nodes

A full node stores the entire blockchain from the genesis block to today, more than 700 GB as of mid-2026 and growing by tens of GB each year. It independently verifies every transaction and block. This is the node that provides the highest security. A pruned node is a full node that has deleted old data after verifying it. It still verifies all the rules, but only stores a few GB of the latest blocks. An SPV node only downloads block headers, it doesn’t fully verify transactions. A mining node is a full node that also actively mines new blocks.

Why run your own node?

Running your own full node means you don’t have to trust anyone. No SPV can deceive you with fake transactions if you have your own node. No exchange or wallet provider can hide information. This isn’t just about individual security. The more people run full nodes, the harder it is for anyone to change Bitcoin’s rules without majority agreement. A node is a vote in Bitcoin’s democracy.

Running a full node doesn’t require special hardware. A Raspberry Pi with an external hard drive is enough. The cost is less than a million rupiah, and its contribution to Bitcoin’s decentralization is real.

Chapter 8 · 8.2
No center, no single point of failure
The P2P Network

Bitcoin has no central server. No headquarters, no data center that can be shut down, no single point that, if attacked, would destroy everything. What exists is a peer-to-peer network: thousands of nodes connected directly to each other.

What is a P2P network?

In a traditional network like a bank or social media, there is a central server that serves all clients. If the server goes down, no client can connect. If the server owner decides to block someone, there is nothing to be done. A P2P network is different. Every participant is equal, none more "central" than another. Information spreads from node to node like gossip. There is no single point of failure.

How do nodes connect?

When a Bitcoin node first starts up, it needs to find peers to connect to. There are several ways: DNS seeds (servers that provide a list of active nodes), hardcoded seed nodes (a list of IPs embedded in the software), and peer exchange (asking an already-connected node to introduce it to other peers). Once connected, the node maintains about 8 regular outbound connections plus 2 block-only ones, and fills the rest with inbound connections. Bitcoin Core caps total connections at 125, which leaves roughly 115 slots for inbound.

How does information spread?

When Alice sends a transaction, her wallet broadcasts that transaction to its connected nodes. A node receives the transaction, verifies its validity, and forwards it to all its peers. Those peers do the same. Within seconds, the transaction has spread to thousands of nodes around the world. This process is called gossiping. Each node only forwards valid transactions.

Why does P2P make Bitcoin strong?

To censor Bitcoin, an attacker would have to block the connection to every node in the world. As long as there’s one accessible node, Bitcoin can be used. Bitcoin has been blocked in various countries, but users there continue to access the network through VPN, Tor, or satellite connections like Blockstream Satellite.

Decentralization isn’t a feature that can be added later. It’s Bitcoin’s fundamental architecture from day one. The P2P network isn’t just how Bitcoin operates, it’s the reason Bitcoin can’t be stopped.

Chapter 8 · 8.3
From one wallet to thousands of nodes in seconds
Transaction Propagation

You press send in your wallet. What happens next?

From wallet to network

The wallet creates a signed transaction and broadcasts it to one or several connected nodes. The first node to receive this transaction is called the origin node from the user’s point of view, even though the network doesn’t really record it that way.

Verification before forwarding

A node that receives a transaction doesn’t forward it right away. It performs a series of verifications first: is the transaction format valid, is the cryptographic signature correct, do the UTXOs being used really exist and are unspent, is the fee reasonable. If everything passes, the transaction enters that node’s mempool and is forwarded to all its peers. If verification fails, the transaction is discarded and not forwarded. This is a natural defense mechanism: spam and invalid transactions die at the first node that receives them.

Node policy vs consensus rules

There is an important distinction that is often misunderstood: consensus rules and node policy are two different things. Consensus rules are the rules that determine whether a transaction or block is valid by protocol. All nodes must agree on these, otherwise they will fork. Node policy is an individual node’s decision about which transactions it wants to accept into the mempool and forward to peers, regardless of whether the transaction is valid by consensus or not.

A concrete example: datacarrier and datacarriersize are two node policy settings available in node software such as Bitcoin Core and Bitcoin Knots. datacarrier controls whether the node will forward transactions that use OP_RETURN to embed arbitrary data. datacarriersize sets the maximum size of that data in bytes. That number is not a protocol rule — its default differs across implementations and has changed between versions. The long-standing convention was 83 bytes (80 bytes of data), and since 2025 it has been at the center of a major debate: one camp wants to relax relay limits, the other wants to keep the filters. Every node operator is free to set their own value. A node that turns off datacarrier will not put OP_RETURN transactions into its mempool and will not forward them to other peers. But if a miner still includes that transaction in a block, the node still accepts the block because OP_RETURN transactions are valid by consensus. Policy stops at the mempool, not at block validation.

This is also the basis of the debate about Ocean Pool that we discuss in Chapter 11: that pool applies transaction filtering based on their own policy, not because the filtered transactions are invalid. A single node or pool can choose a different policy from the majority without violating consensus, but the consequence is that the transactions they reject still end up on the blockchain through miners or other nodes that don’t apply the same filtering.

Flooding and deduplication

Transaction propagation uses a flooding mechanism: every node that receives a valid transaction forwards it to all peers. But this creates a problem because a node can receive the same transaction from many peers at the same time. The solution is deduplication. Each node keeps a list of transactions it has already seen. If the same transaction comes again, it is immediately discarded without being reprocessed.

How long until it reaches the whole network?

Under normal conditions, a transaction spreads to most nodes around the world in less than 5 seconds. Reaching 90% of nodes usually takes about 10-15 seconds. This is well before the transaction is confirmed on the blockchain, which takes an average of 10 minutes.

Privacy in propagation

There is an interesting privacy issue: the first node to broadcast a transaction is most likely the original sender or directly connected to it. An observer monitoring many nodes can try to identify the transaction’s origin. The most widely discussed solution for this is Dandelion++: the transaction is first forwarded quietly along a single path (stem phase) before finally being spread to the whole network (fluff phase). This makes the transaction’s origin much harder to trace. Worth noting, Dandelion++ has not been merged into Bitcoin Core, and we cover why in 18.6.

Transaction propagation is one of the most elegant processes in Bitcoin. Thousands of nodes that don’t know each other, no central coordination, but within seconds the information has spread to every corner of the world. All because every node follows the same rules.

Chapter 8 · 8.4
A new block must spread as fast as possible — milliseconds mean money
Block Propagation

Transaction propagation and block propagation have the same goal: spreading information to the whole network as fast as possible. But a block is much larger than a transaction, and the stakes are much higher: a miner who finds a new block wants the whole network to recognize it as fast as possible before another miner finds the next block.

From miner to network

When a miner finds a valid nonce, it immediately broadcasts the new block to all its peers. Every node that receives the block performs full verification: is the proof of work valid, are all the transactions inside it valid, does the block header connect to the previous block correctly. If everything passes, the block is accepted, added to the local chain, and forwarded to all peers.

The problem: blocks are too big

A Bitcoin block can be up to 4 MB with SegWit weight. Spreading 4 MB to thousands of nodes requires significant bandwidth. In Bitcoin’s early days this wasn’t a problem because blocks were rarely full. But when the network is busy, propagation delay can cause serious problems.

Compact Block and Header-First

The main solution is Compact Block (BIP 152): instead of sending the entire block, a node sends the block header plus a list of shortened transaction IDs. The recipient most likely already has almost all of those transactions in its mempool. It only needs to request the transactions it doesn’t yet have. This reduces the data sent drastically, from megabytes to kilobytes. Header-First propagation is another technique: a node broadcasts the block header first before the entire block is ready, allowing proof of work validation to start earlier.

Orphan blocks and why speed matters

There is a phenomenon called an orphan block: two miners find a valid block at almost the same time. The network is temporarily split into two versions of the chain. Eventually the longer chain wins, and the block in the shorter chain becomes an orphan, valid but not recognized. The slower the propagation, the greater the chance of an orphan block. Compact Block has already significantly reduced the orphan rate.

Block propagation speed is one of the most important health metrics of the Bitcoin network. Thanks to Compact Block, a new block can reach most of the network within seconds. In the era before Compact Block, the same process took many times longer because the entire contents of a block had to be resent to every peer.

Why does Compact Block reduce the orphan rate?
A regular block takes several seconds to spread to the whole network. During that window, other miners who haven’t received the new block keep mining on top of the old block, increasing orphan risk. Compact Block shortens this window to less than 1 second and the orphan risk drops drastically.
What happens to the transactions in an orphan block?
The transactions in an orphan block are returned to the mempool and can be confirmed in the next block. No bitcoin is lost. The only one who loses is the miner who found the orphan block.
Chapter 8 · 8.5
How does a new node find its place in the network?
Connections and Peer Discovery

In 8.2 we mentioned three ways a node finds peers. This section takes each of them apart, because this is where one of the answers lives to why Bitcoin is so hard to block.

A new Bitcoin node starting up for the first time faces one fundamental problem: how does it find other nodes to connect to? It doesn’t know anyone’s address. The P2P network has no centralized directory. But within minutes, that new node is already connected to dozens of peers around the world.

DNS Seed

The first and most common way is through a DNS seed. Bitcoin node software, like Bitcoin Core, Bitcoin Knots, or other implementations, generally embeds a few special domain names in its code. When a node first starts, it does a DNS query to these domains and gets a list of IP addresses of nodes that are currently active. DNS seeds are managed by trusted people in the Bitcoin community. This isn’t a dangerous trust point because the node only uses it to find initial peers, and after that all verification is done independently.

Peer Exchange

After connecting to the first few nodes, the new node can request a list of known peers through the getaddr message. A node that receives this request replies with an addr message containing a list of IP addresses of other nodes it knows. From here the network of connections grows organically without central coordination.

Hardcoded Seeds

If the DNS seed can’t be reached, there’s a fallback: a list of IP addresses embedded directly in the software code. These are nodes known to be stable and long-running. This list is updated every few releases by each development team.

Maintaining connections

A Bitcoin node generally maintains about 8 outbound connections that it chooses itself and accepts inbound connections from other peers. Connections are kept alive with periodic ping and pong messages. A node that doesn’t respond is disconnected and replaced. A node also stores a peer address database locally so that when it’s shut down and started again, it can connect directly to known peers without having to start peer discovery from scratch.

Why is this important for decentralization?

Bitcoin’s peer discovery system is designed not to depend on a single point. The DNS seed can fail or be blocked, but there are still hardcoded seeds. Hardcoded seeds can become outdated, but there’s still the peer database from previous sessions. And if all of that fails, the user can enter a peer address manually.

One of the most effective ways to support the Bitcoin network is to run a node with open inbound connections. A node like this helps new nodes find peers and strengthens the network’s resilience as a whole.

Chapter 8 · 8.6
Technical and social, both equally important
Keeping the Network Healthy

A healthy Bitcoin network isn’t just about the number of nodes. It’s about the quality of connections, diversity of locations, diversity of software, and the often-forgotten one: the diversity of the humans behind those nodes.

The network’s technical health

There are several technical health indicators that can be monitored. The number of reachable full nodes is the most basic indicator. The more there are, the stronger it is. The geographic distribution of nodes is also important: a network whose nodes are all concentrated in one country is far more vulnerable to regulation or an internet outage than a network spread evenly around the world. Software diversity is also crucial. If almost all nodes run the same implementation, a critical bug in that implementation could affect the network widely.

What you can do as a node runner

First, leave inbound connections open. A node that accepts inbound connections helps new nodes find peers and strengthens the network. Second, keep uptime up. A node that’s frequently offline doesn’t contribute much. A small device running 24 hours is far more valuable than a computer that only turns on occasionally. Third, update the software regularly, not because you follow one development team, but because security patches are important to protect yourself and the network.

The network’s social health

This is the part that is often ignored but just as important. Node runners are the people most committed to Bitcoin. They spend time, money, and energy running the infrastructure that makes Bitcoin work. And precisely because of that great commitment, debates among them can become very heated.

Debates about block size, mempool policy, soft forks, software choice, how to operate a node: all of these are legitimate and important debates. Disagreement is healthy. Disagreement is a sign that many people are thinking independently, not just following one leader.

But there’s a difference between disagreeing and being disrespectful. Someone can have a different opinion about mempool policy while still respecting that another person has spent time and energy running their own node. Someone can criticize a technical decision without attacking the person’s character.

The ecosystem isn’t a monolith

Bitcoin is an open protocol. No single entity can claim full authority over it. No single development team, no single software implementation, no single discussion forum holds the single truth. This isn’t a weakness. It’s one of Bitcoin’s greatest strengths. As long as people with different views can still find common ground in running the network, Bitcoin will keep surviving.

Running a node is a real action, not just an opinion on the internet. Whatever debate is happening out there, a node that stays on is a contribution that always matters. And treating fellow node runners with respect, even when you disagree, is part of keeping the network healthy.
