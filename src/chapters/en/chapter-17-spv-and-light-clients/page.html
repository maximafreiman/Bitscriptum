Chapter 17 · 17.1
Satoshi already thought about this in 2008 — how a phone can verify Bitcoin
The Problem SPV Solves

Imagine you want to verify that a check was really issued by a legitimate bank. There are two ways: first, you become a bank employee and access the entire database system to verify it yourself. Second, you ask the bank to show you proof of the transaction with an official stamp whose authenticity you can verify without entering the system.

A full node is the first way: full verification but it requires a big commitment. SPV is the second way: lighter verification but still reliable for most use cases.

Historical context: Satoshi already thought about this

In section 8 of the Bitcoin whitepaper (2008), Satoshi wrote about Simplified Payment Verification. He realized that not everyone would or could run a full node. For everyday users who just want to receive and send payments, there’s a lighter way: just verify that your transaction is in a valid block, without needing to validate the entire blockchain.

The key is in the block header. A Bitcoin block header is only 80 bytes per block, but contains the merkle root, a hash that represents all the transactions in that block. By using only the block headers (about 70 MB for the entire blockchain) plus a merkle proof for a particular transaction, you can prove that the transaction is in a valid block.

What can SPV verify?

An SPV client can verify that a transaction is in a particular block via a merkle proof, that the block has valid proof-of-work via the header, and that the block is part of the longest chain via the header chain. What SPV can’t verify without additional trust: whether the other consensus rules are met, whether the transaction was double-spent before entering the block, and whether the total Bitcoin supply is valid.

The trust assumption SPV needs

SPV isn’t trustless like a full node. It depends on the assumption that the majority of hashrate is honest. If the majority of miners collude, they can create a fake block that deceives the SPV client. But this assumption is the same as Bitcoin’s overall security assumption: as long as the majority is honest, SPV is safe for everyday payments.

Who is SPV suitable for?

For everyday payments of moderate amounts, SPV provides a good balance between security and convenience. For very large-value payments or for needs that require full verification, a full node remains the best choice.

SPV isn’t a bad compromise, but rather a deliberate trade-off that Satoshi thought about from the start. In a majority-honest system, SPV provides verification strong enough for most use cases. The key is understanding its limitations and choosing a level of verification that matches your needs and the value at stake.

Chapter 17 · 17.2
Proving one transaction out of millions — with just a few dozen bytes
Merkle Proof — Efficient Membership Proof

Imagine you live in a city of 10,000 residents and need to prove that your name is in the official residency register. There are two ways: first, show the whole book (650 pages) to the person who wants to verify. Second, show one small path from your name up to the official stamp on the first page, only 13 steps for 10,000 residents, not 10,000 pages.

That’s a merkle proof. Not proof by showing all the data, but proof by showing a path that can be cryptographically verified.

A different perspective from Chapter 3

In Chapter 4 we saw the merkle tree as a cryptographic structure: how transaction hashes are combined into one merkle root. Here we see it from the SPV client’s perspective: how your phone proves that your transaction is in a block it never fully downloaded.

The structure of a merkle proof

Suppose a block has 8 transactions. To prove that Tx3 is in this block, you don’t need all 8 transactions. You only need: the hash of Tx4 (Tx3’s pair at the first level), the hash of H(Tx1+Tx2) (the pair at the second level), and the hash of H(Tx5+Tx6+Tx7+Tx8) (the pair at the third level). These three hashes, combined with Tx3, are enough to reconstruct the merkle root. If the result matches the merkle root in the block header whose proof-of-work has been verified, the transaction is proven to be in that block.

Remarkable efficiency

For a block with n transactions, a merkle proof only needs log₂(n) hashes. A modern Bitcoin block can contain more than 3,000 transactions. Its merkle proof only needs about 12 hashes, 32 bytes each, totaling about 384 bytes. Compare that with downloading the entire block, which can reach 1-2 MB. If the transactions in a block double from 3,000 to 6,000, the proof only needs one additional hash.

How an SPV client uses a merkle proof

When your SPV wallet receives a payment, here’s what happens behind the scenes: the connected node sends the transaction along with its merkle proof. The SPV client takes the transaction hash, follows the merkle proof path, and reconstructs the merkle root. Then it compares that with the merkle root in the block header whose proof-of-work has been verified. If they match, the transaction is proven to be in that block.

Limitations of a merkle proof

A merkle proof proves that a transaction IS in a block, but doesn’t prove that the transaction is VALID. A transaction’s inputs could already have been spent earlier and the block containing that transaction would still be valid from a proof-of-work perspective. To detect a double spend, you need access to the UTXO set, which only a full node has.

The merkle proof is one of the most elegant cryptographic constructions in Bitcoin. With only a few dozen bytes, anyone can prove that a transaction is inside a block containing millions of bytes of data. This is a mathematical consequence of the deterministic and collision-resistant nature of a hash function.

Chapter 17 · 17.3
A mathematically elegant solution that turned out to leak on the privacy side
Bloom Filters — The Old, Problematic Way

An SPV client needs to tell a full node: "send me the transactions relevant to my address." But if the SPV directly says "I have address bc1q...xyz, send me transactions to that address," privacy leaks immediately because the full node knows exactly which address you own.

Bloom filters were Bitcoin’s first solution to this problem. Introduced in BIP 37 in 2012, they let an SPV client tell a node about relevant transactions without directly revealing the address.

What is a bloom filter?

A bloom filter is a probabilistic data structure that answers one question: "is element X in this set?" The answer "no" is always correct, if the bloom filter says it’s not there, it really isn’t. But the answer "yes" can be wrong (a false positive), the bloom filter can say "yes" for an element that isn’t actually in the set. This is intentional: false positives create ambiguity that protects privacy.

How a bloom filter works

A bloom filter is a bit array, starting with all bits zero. To add an element, you hash that element with several different hash functions, then set the resulting bits to 1. To query "is X there?", hash X with the same hash functions. If all the resulting bits are already 1, X might be there. If even one bit is still 0, X is definitely not there. The SPV client builds a bloom filter containing its addresses and sends it to a node. The node filters transactions and only sends the matching ones.

The privacy problem that made BIP 37 deprecated

Despite the clever design, bloom filters have a serious problem. The size and composition of the filter can reveal information about how many addresses the client owns. A malicious node can test millions of Bitcoin addresses against the filter and do statistical analysis to identify the addresses actually owned. Early BIP 37 implementations even had a weakness that let a full node determine the client’s addresses with surprising accuracy.

Besides the privacy problem, BIP 37 also burdened full nodes disproportionately, because a node has to filter every transaction for every connected SPV client, which can become a DoS attack.

Current status

BIP 37 is now considered deprecated. Many nodes disable BIP 37 support by default. A better solution, compact block filters (BIP 157/158), is already available and will be discussed in 17.4.

The bloom filter is an interesting example of a mathematically elegant solution that isn’t good enough in security practice. Privacy is a very hard property to maintain, even a system designed to protect privacy can leak information through unexpected channels.

Chapter 17 · 17.4
If you don’t need to tell anyone what you’re looking for, don’t do it
BIP 157/158 — Compact Block Filters: A Better Privacy Solution

BIP 37 lets the node filter for the client, so the node knows what the client is looking for. BIP 157/158 flips this logic: the client downloads filters and filters them itself. This simple shift creates a huge privacy difference.

The inverted logic

With BIP 37: the SPV client says to the node "I have this address, please filter for me." The node knows the address being searched. With BIP 157/158: the node creates a compact filter for each block that summarizes all the data in that block. The SPV client downloads this filter and checks for itself whether there’s any relevant data. If there is, only then does the client download the full block. The node never knows what the client is looking for.

What is a compact block filter?

BIP 158 defines a compact filter format using a data structure called a Golomb-Coded Set (GCS). A GCS is a probabilistic data structure that’s more efficient than a bloom filter with a more predictable false positive rate. For each block, the node creates a filter containing all the scriptPubKeys of the transaction outputs in that block. This filter is about 10-20 KB for a block with thousands of transactions.

BIP 157: The Filter Distribution Protocol

BIP 157 defines how these filters are distributed across the P2P network. There are two new message types: getcfheaders to request filter headers, and getcfilters to request filters for a particular block range. A client can download filter headers lightly first, then download the full filters only for the blocks it needs.

A trade-off to understand

An SPV client with BIP 157/158 has to download the filter for every block, totaling a few hundred MB to a few GB for the entire chain. This is larger than BIP 37, which only downloads relevant transactions. In exchange, the privacy gained is far better. This is a deliberate trade-off: trade bandwidth for privacy.

Implementation status

BIP 157/158 is already implemented in major Bitcoin client software. Neutrino is a Go light client implementation that uses BIP 157/158 and is used by Lightning Network mobile wallets like Phoenix and Breez.

BIP 157/158 shows how better protocol design can flip trust assumptions. By moving the filtering work from the node to the client, privacy increases drastically without sacrificing security. If you don’t need to tell anyone what you’re looking for, don’t do it.

Chapter 17 · 17.5
SPV can be deceived in certain scenarios — but how realistic and how expensive?
SPV vs Full Node Trade-off — How Big Is the Risk That SPV Can Be Deceived?

SPV doesn’t verify all consensus rules. But how big is the real risk? This is a question often answered wrong in two directions: some say SPV is as safe as a full node, others say SPV can’t be trusted at all. Both are wrong.

What can an attacker do to an SPV client?

The most realistic attack scenario is an eclipse attack: the attacker isolates the SPV client from the honest network and only connects it to nodes owned by the attacker. From this position, the attacker can hide incoming transactions or show a different chain. For a double spend, the attacker needs an eclipse attack AND significant hashrate to produce an alternative chain, which is very expensive and rare.

What an attacker CANNOT do

Without controlling the majority of the network’s hashrate, an attacker can’t create a transaction that spends bitcoin they don’t own because it needs a private key, create bitcoin out of nothing because it violates consensus that any full node can detect, or convince an SPV client to accept a block without valid proof-of-work because SPV still verifies the PoW header.

Confirmations as mitigation

The more confirmations you wait for, the more expensive it is for an attacker to carry out an attack. For everyday small-value transactions, 1-3 confirmations is already plenty. For large values, 6+ confirmations provide far stronger security even for SPV.

Practical conclusion

For 99% of everyday Bitcoin use by individuals, buying coffee, receiving a salary, sending to a friend, SPV provides more than enough security. A full node remains ideal for receiving large-value payments, running a business that accepts Bitcoin, and anyone who wants full self-verification without any trust assumptions.

Bitcoin’s security isn’t binary between "safe" and "unsafe," but rather a spectrum of trade-offs between convenience, resources, and the level of verification. SPV is a valid point on that spectrum, not an embarrassing compromise. What matters is understanding where that point is and choosing deliberately.

Chapter 17 · 17.6
SPV in the whitepaper and SPV in the app store are two different things
Light Clients in the Real World — Electrum, Neutrino, and Modern Wallets

Everything we learned in Chapter 17 about SPV, merkle proofs, bloom filters, and compact block filters isn’t a theoretical concept, but rather all of it is implemented in Bitcoin wallets used by millions of people every day. But real-world implementations are often more complex and varied than the pure SPV model Satoshi described in the whitepaper.

Electrum: SPV Hybrid with a Server

Electrum is one of the most popular Bitcoin wallets since 2011. Electrum doesn’t implement pure SPV, but rather connects to a network of Electrum servers that have already processed the blockchain and store the UTXO set. The Electrum client can query the server for balance, historical transactions, and UTXOs very quickly. If you run your own Electrum server on top of a full node, you get Electrum’s query speed with full-node-level privacy.

Neutrino: True BIP 157/158

Neutrino is a Bitcoin light client implementation in Go developed by Lightning Labs. It fully implements BIP 157/158 (compact block filters). Neutrino is used as the backend for several Lightning Network mobile wallets like Phoenix Wallet and Breez. To pay a Lightning invoice, those wallets use Neutrino to verify the channel state on the Bitcoin blockchain without downloading the entire blockchain.

Ordinary "SPV" Mobile Wallets: Most Use a Server

Many mobile wallets that claim "SPV" actually connect to a backend server controlled by that wallet’s developer. They don’t download the header chain or do any PoW verification at all, but rather just query the developer’s server API to get balance and transactions. This isn’t SPV, it’s custodial-lite: you hold the private key but verification is done by someone else.

Choosing the right one

There’s no single right answer for everyone. For 99% of everyday users with small amounts, an ordinary mobile wallet is already safe enough. For users who care about privacy and verification, Electrum with your own server or Neutrino is a far better choice. For large values or business needs, a full node remains the best choice.

What matters most is understanding the trust model of the wallet you use. "Self-custody" doesn’t always mean "trustless," because many self-custody wallets quietly require trust in a server operator or developer. Choose deliberately based on the value you store and the level of trust you need.
