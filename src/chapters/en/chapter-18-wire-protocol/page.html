Chapter 18 · 18.1
Behind every Bitcoin transaction you send, there’s a very strict binary conversation between thousands of computers
P2P Architecture & Wire Message Structure

Chapter 8 explained Bitcoin’s P2P network in terms of what happens. Chapter 18 covers the how: which bytes exactly move between nodes. If Chapter 8 was the map of the city, Chapter 18 is its road signs and traffic rules.

Imagine two people talking over a walkie-talkie with a military protocol. Every transmission must start with the station identification code, followed by the command code, then the message body, then the verification code. You can’t just talk freely; if the format is wrong, the transmission is ignored. The Bitcoin wire protocol works exactly like that, except it’s not the human voice being sent, but binary bytes that follow very strict rules.

If you open Wireshark and look at the traffic between two Bitcoin nodes, you won’t see HTTP, no JSON, no REST API. What you see is a raw byte stream, a binary format designed for maximum efficiency, not human readability.

A network without a central server

Bitcoin runs on top of a pure, unstructured peer-to-peer network. There’s no central server, no coordinator, no single point of failure. Every node is both a client and a server, it receives data from other peers while also serving data to other peers. This is different from how the ordinary internet works, where you are the client and Google, YouTube, or your bank is the server.

Every node maintains two kinds of connections. Outbound connections (8 regular + 2 block-only) are connections you initiate yourself, where you choose the peer. Inbound connections (roughly 115, since Bitcoin Core caps total connections at 125 and 10 of those are already used by outbound) are connections initiated by other peers that come to you, if port 8333 is open. Outbound connections are more trusted because you choose who to talk to, rather than passively accepting anyone who comes knocking.

How does a node find someone to talk to?

When first run, a Bitcoin node doesn’t know anyone yet. It uses DNS seeds, like a special phone book, to get a list of IPs of active nodes. There are several DNS seeds maintained by trusted contributors. After connecting to a few peers, the node exchanges lists of acquaintances via addr messages, like friends recommending new acquaintances to each other. This list is stored in peers.dat for use on restart.

Anatomy of one Bitcoin message

Every Bitcoin P2P message, whatever its contents, always has the exact same header structure. It’s like a standard envelope that always has a "sender," "recipient," and "contents" field in the same place, so whoever receives the envelope immediately knows how to read it.

The magic bytes (4 bytes) are the network identifier code. Like the area code in a phone number: 0xF9BEB4D9 means "this is a Bitcoin mainnet message." If the first byte a node receives differs from what it expects, the connection is closed immediately without reading the rest.

The command (12 bytes) is the command name in ASCII text. "version", "inv", "tx", "block", always padded with null bytes up to 12 characters. Like an email subject that always has exactly the same length.

The length (4 bytes) tells the recipient how many payload bytes are coming. This is important so the recipient knows when one message ends and the next begins in the continuously flowing byte stream.

The checksum (4 bytes) is the first 4 bytes of SHA256(SHA256(payload)). If the payload is corrupted in transit, the checksum won’t match and the message is ignored. Like a serial number on a banknote that can detect forgery.

Services Flags: A Node’s Capability Business Card

Inside the version message, every node advertises what it can do via services flags. It’s like a LinkedIn profile listing skills: NODE_NETWORK means "I have the full blockchain and can serve historical blocks," NODE_COMPACT_FILTERS means "I support BIP 157/158 for modern SPV clients," NODE_WITNESS means "I support SegWit." Peers read these flags to decide what can be requested from that node.

Bitcoin’s binary, minimal wire format is a deliberate design decision. There’s no overhead from a text format like HTTP or JSON, every byte has a specific meaning. This lets a node process thousands of messages per second with very little CPU overhead. Simplicity at the protocol level is what makes complexity at the network level possible.

Before they can exchange data, two nodes must first complete a three-step ritual
Handshake & Message Flow — The Language Two Nodes Use When They First Meet

Imagine two diplomats from different countries meeting for the first time. There’s a protocol to follow before they can discuss important matters: a formal introduction, identity verification, confirmation that both speak the same language, and only then move on to substance. Bitcoin nodes work exactly like that.

Handshake: three steps before they can talk

When two nodes first connect, they don’t immediately exchange transactions or blocks. There’s a three-step ritual that has to be completed first. The node that initiates the connection sends a version message containing the software version, services flags, timestamp, user agent, and the highest known block height. The receiving node replies with its own version. Then both send a verack as confirmation. After both veracks are received, the handshake is complete and the official communication session begins.

The nonce in the version message has a special function: detecting a self-connection. If a node receives a version with the same nonce it sent, it means it accidentally connected to itself through a relay or a strange network configuration. The connection is closed immediately.

Transaction lifecycle: from wallet to network

When you send a Bitcoin transaction from your wallet, three P2P messages work in sequence. First, the node announces the txid via inv without sending the full data, like a "new product available" poster without forcing everyone to grab it. A peer that doesn’t have the transaction yet replies with getdata. Only then is the full transaction sent via tx. A peer that already has the transaction from another node doesn’t need to respond at all, so there’s no redundant data transfer.

Propagation spreads like ripples in water: one transaction can reach the entire network in seconds via this flooding process.

Block propagation: three generations of mechanisms

When a miner finds a new block, propagation must be as fast as possible. Every second of delay increases the risk of another block being found before this one spreads, causing a stale block that wastes the miner’s reward.

The old way uses the classic inv/getdata/block, where the full 1-2 MB block must be sent to every peer that requests it. A better way is headers-first: send the 80-byte header first so the peer can verify the proof-of-work before deciding whether it needs the full block. The best way is compact blocks (BIP 152), discussed in 18.4: send a sketch of the block that can be reconstructed from the mempool, so only a small fraction of the data needs to be transferred.

Other supporting messages

getheaders requests block headers from a peer to build a picture of the chain quickly without downloading full blocks. addr and addrv2 share lists of known peer IP addresses, continuing the peer discovery process that started from DNS seeds. feefilter lets a node tell a peer the minimum fee it accepts in its mempool, so transactions with too low a fee aren’t sent at all.

The inv/getdata design that separates announcement from data delivery is a very important efficiency decision. Without it, every new transaction would be sent in full to all peers redundantly. With inv/getdata, each piece of data is only sent to the peer that actually needs it, saving network bandwidth significantly.

Chapter 18 · 18.3
A new node can’t just trust data from one peer — it has to know which chain is correct before starting to download
Block Sync — From One Block to the Whole Blockchain

In Chapter 16 we discussed IBD from the node’s perspective: what gets verified and how long it takes. Here we look at it from a different angle: what P2P messages are actually sent during the sync process, and why there are two sync strategies with very different efficiency.

Strategy 1: Blocks-first sync, the abandoned way

The most naive way is to request blocks one by one from a single peer. The node sends getblocks with a block locator, the peer replies with an inv containing up to 500 of the next block hashes, then the node requests each block via getdata and waits for it to be validated before requesting the next. The problem: the entire sync depends on a single peer. If the peer is slow, everything is slow. The node also can’t tell whether it’s on the correct chain until it has already downloaded many blocks.

Strategy 2: Headers-first sync, the modern way since 2015

Headers-first solves this problem by separating two phases. First phase: download all headers via getheaders. The peer replies with up to 2,000 headers per response (each header 80 bytes plus 1 byte varint, about 162 KB per response). Within a few minutes, the node has all the headers from genesis to the tip, about 70 MB total. From this header chain, the node can compute the accumulated proof-of-work of each chain offered by various peers and know which is valid, even before downloading a single full block.

Second phase: download blocks in parallel from many different peers. Since the order is already known from the header chain, the node can request blocks from any peer without the risk of being tricked by a wrong order.

Block locator algorithm

The block locator is a clever, economical list of hashes. The node doesn’t send the hashes of all the blocks it has, but rather chooses them exponentially sparse: the 10 most recent blocks one by one, then every 2 blocks, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048, and so on up to the genesis block. This lets a peer efficiently find the chain divergence point even with a very long reorg, using only about 40 hashes, even for a chain hundreds of thousands of blocks long.

Minimum chain work threshold

For extra security, modern nodes have a minimum chain work threshold: the minimum accumulated proof-of-work a chain must have before it’s considered worth following. This prevents a node from being tricked into following a fake, very short chain with very little PoW, even before the header chain is fully verified.

The shift from blocks-first to headers-first is one of the biggest improvements in Bitcoin Core’s history (version 0.10.0, 2015). By separating chain verification from data download, IBD became far faster, safer, and more resistant to misbehaving peers.

Chapter 18 · 18.4
Why download data you already have? Compact blocks solve the biggest inefficiency in block propagation
Compact Blocks — Speeding Up Block Propagation (BIP 152)

Imagine someone sends you a copy of a 200-page newspaper, when you already have 198 of its pages. A waste of time and paper, right? That’s what happened with block propagation before compact blocks: every node had to download the full block (~1-2 MB) even though it already knew almost all the transactions in it from its own mempool.

The problem being solved

A node well-connected to the network usually already has 95-99% of the transactions in a block before the block is found. This is because transactions are propagated across the network when first sent, long before they enter a block. Compact blocks (BIP 152, 2016) take advantage of this fact: instead of sending the whole block, send just a list of short transaction IDs and let the recipient reconstruct the rest from its local mempool.

The cmpctblock message format

The cmpctblock message contains three main components. The block header (80 bytes) the same as usual, containing the proof-of-work, merkle root, and timestamp. Shortids of 6 bytes for each transaction in the block (much smaller than the 32-byte txid), created with SipHash-2-4 using a unique nonce per block so they’re only valid for this block. Prefill transactions, a few transactions sent directly without a shortid, especially the coinbase transaction, which is guaranteed not to be in any mempool.

The recipient matches each shortid against a transaction in its mempool. Found transactions are used directly to reconstruct the block. If a shortid doesn’t match, the recipient sends getblocktxn with a list of the transaction indices it needs, and the sender replies with blocktxn containing only those transactions.

High-bandwidth vs low-bandwidth mode

These two modes are negotiated via the sendcmpct message during the handshake. High-bandwidth mode (sendcmpct(1)): the node sends the cmpctblock unsolicited as soon as a new block is found, suitable for a maximum of 3 peers with trusted, low-latency connections. Low-bandwidth mode (sendcmpct(0)): the node announces via inv or headers first, and only sends the cmpctblock if the peer requests it via getdata.

Real-world impact

Compact blocks reduce the data transferred from ~1,500 KB to ~20-60 KB under normal conditions. This is equivalent to a 95-98% reduction in bandwidth for block propagation. Block propagation latency drops drastically because less data has to be transferred and verified.

Compact blocks are an elegant example of the principle "don’t send data the recipient already has." By taking advantage of the fact that the mempools of well-connected nodes are almost always in sync, BIP 152 turns block propagation from a bandwidth-heavy operation into a near-real-time one.

Chapter 18 · 18.5
If compact blocks solve block propagation, Erlay solves transaction propagation — with a very elegant mathematical approach
Erlay — More Efficient Transaction Propagation (BIP 330)

Imagine you live in a village of 1,000 residents. There’s fresh news: "The village head got married again." The old way: everyone who knows immediately tells all their neighbors. The same news can be heard by one person from 10 different people before they get a chance to pass it on. A waste of conversation. Erlay is a smarter way: exchange a list of news periodically, and only tell what’s genuinely new.

The flooding problem we have now

Currently transaction propagation uses a flooding mechanism via inv/getdata/tx. Every new transaction is announced to all peers via inv. The result: each transaction is announced on average 8-16 times to each node, almost all of it redundant. On a network with 10,000+ nodes and hundreds of thousands of transactions per day, the bandwidth overhead from this redundancy is very significant and limits how many connections a node can maintain without large bandwidth.

Set reconciliation: Erlay’s core idea

Erlay (BIP 330) introduces a technique called set reconciliation. For a small subset of chosen peers, the node still uses flooding as usual (fanout) to ensure fast propagation. For the other peers, the node periodically exchanges a very compact sketch of its transaction set using a data structure called minisketch. From the two exchanged sketches, both can learn which transactions are held by only one side, without needing to send the full list.

Minisketch: clever mathematics

Minisketch is an implementation of PinSketch, a set reconciliation technique built on BCH codes. It lets two parties learn the difference between their sets by transferring only as much data as the difference, not as much as the total set. If node A and node B each have 10,000 transactions and differ by only 50 transactions, the sketch sent is only about 50 elements in size, not 10,000. It’s like a small "fingerprint" of the collection that’s enough to mathematically reveal the difference.

Long-term impact

Erlay reduces transaction propagation bandwidth by about 40%. More importantly: because each peer connection needs less bandwidth, a node can maintain more peer connections without proportional overhead. More connections means a more decentralized network that’s more resistant to eclipse attacks. Transaction propagation latency barely changes because fanout to several peers is still done.

Erlay is an example of how mathematical theory (error-correcting codes and set reconciliation) can be applied to solve a practical problem in a P2P network. The result isn’t just bandwidth savings, but an improvement in network decentralization, which is one of Bitcoin’s most valuable properties.

Chapter 18 · 18.6
You can verify transactions without your identity being known — but transaction propagation can expose your IP address before the transaction enters a block
Dandelion & Transaction Privacy (BIP 156)

We mentioned Dandelion in 8.3 as the most widely discussed answer to the privacy problem in propagation. Here we look at how it works, and also at why it still has not made it into Bitcoin Core.

Imagine you’re standing in the middle of a crowd and shout "I have this letter!" Everyone immediately knows you’re the sender. That’s what happens with Bitcoin transaction propagation today: the node that first spreads a transaction to the network is almost certainly the sending node.

How transaction propagation exposes the sender’s IP

When you create a transaction, your node is the first to spread it via flooding. An attacker running many nodes can observe from which node a transaction is first seen. The node that first broadcasts a transaction to many different peers is most likely the original source. This isn’t a theoretical attack, and blockchain analytics companies have long used this technique to link Bitcoin transactions to the sender’s IP address.

Dandelion: stem phase and fluff phase

Dandelion (BIP 156) solves this problem in an elegant way. Its name comes from the dandelion flower: a thin stem at first, then bursting out in all directions. In the stem phase, a new transaction isn’t immediately flooded to all peers. Instead, it’s forwarded to one peer at random, then that peer to one more peer, for several hops. During the stem phase, the transaction doesn’t enter the normal mempool, but is only forwarded silently. In the fluff phase, after a few hops, one node randomly decides to start spreading the transaction normally via flooding. The node that starts the fluff isn’t the original sender, so an attacker can’t determine the true source.

Dandelion++: A Refinement of the Original Version

The original BIP 156 has a weakness: if an attacker is on the stem path, they can trace it. Dandelion++ fixes this by choosing a different stem peer for each transaction from a stable, random subset of peers, so an attacker can’t predict or influence the stem path.

Implementation status

Dandelion++ hasn’t been merged into Bitcoin Core because of implementation complexity and concerns about potential new DoS attacks that could be exploited via the stem phase. Instead, Bitcoin Core uses a simpler technique: transactions are sent with a random delay to make timing analysis harder, though not as effective as Dandelion.

Privacy in Bitcoin isn’t just about hiding transaction amounts or on-chain identity, but also about hiding where a transaction originates at the P2P network level. Dandelion is one of the cleverest attempts to solve this problem without sacrificing transaction propagation speed.

Dandelion splits transaction propagation into two very different phases. The stem phase is hidden, the fluff phase is like ordinary flooding but from an unexpected point.
Why is it called Dandelion (the dandelion flower)?
A dandelion flower has a thin, long stem, then at its tip tiny seeds scatter in all directions when the wind blows (fluff). A Bitcoin transaction in Dandelion moves exactly like that: silent and linear at first, then bursting out across the entire network from one unexpected point.
PHASE 1 — STEM PHASE
The Dandelion Stem — Silent Propagation
The transaction is forwarded one by one linearly, not entering the normal mempool.
The node picks one peer at random
That peer forwards to one more peer
Continues for ~2-10 hops
No flooding, no mempool
The attacker can’t distinguish the original source from a forwarder
Like whispering from ear to ear — no one outside can hear
PHASE 2 — FLUFF PHASE
Dandelion Bursts — Normal Flooding
After a few hops, one node decides to start flooding as usual.
The node chooses at random: keep stemming or start fluffing
Fluff probability: ~10% per hop
On fluff: the transaction enters the mempool and is flooded to all peers
From here, propagation is as usual
The node that starts the fluff isn’t the original sender
Like someone in the middle of a crowd suddenly announcing — it doesn’t mean they’re the sender

Dandelion++ vs the original Dandelion (BIP 156):
The original Dandelion is vulnerable: if an attacker is on the stem path, they can trace it. Dandelion++ fixes this by choosing a different stem peer for each transaction from a stable subset of peers, so an attacker can’t predict or influence the stem path.
